# Fix plan for BUG_UNIVERSAL_KEY_SHORT_NAME

Status: **reviewed (three rounds), revised, ready to execute. Nothing implemented
yet.** Drafted and revised 2026-08-12.

This document is meant to be executable on its own, without the conversation that
produced it. Part A repairs the key computation in `contrib/Isabelle_RPC`; Part B
rebuilds the semantic store on `cslh19` under the repaired keys. The defect itself
is diagnosed in `BUG_UNIVERSAL_KEY_SHORT_NAME.md` — that document is the evidence,
this one is the response. The position work that surfaced it is
`contrib/Semantic_Embedding/ENTITY_POSITION_PLAN.md` (§18 records the sweep whose
17 % shortfall started this).

**Execution order** (§E gives the detail): Part A, then its acceptance measurements,
then the dump, then the join, then the gap list, then the swap. Every write on
`cslh19` — including the scratch dump — needs the user's approval for that specific
run (D6).

## 0. Decisions already taken

From the user. Not open for review; recorded so the plan's assumptions are visible.

- **D1.** The rescue builds a **new store** and swaps whole directories at the end.
  It never mutates the existing store in place.
- **D2.** The rescue runs **on `cslh19`** — the store and the `AFP-ALL-4` image are
  there and nowhere else.
- **D3.** Scope is **our own data**. Part A is followed immediately by Part B and
  only then by a release, so the "Part A shipped alone" scenario does not arise and
  is not defended against: no key-scheme marker, no `SCHEMA_VERSION` bump, no CI
  key-provenance gate, no publication freeze. **Downstream users' own user-layer
  records are written off** — §B.11 records what that costs them, for the release
  note.
- **D4.** `Universal_Key.constituents_cache` is **kept and re-scoped**, not deleted:
  it moves into `Theory_Data` behind a shared mutable reference, paired with the set
  base name → long name claims map, and a colliding theory forks a filtered copy with
  the colliding entries dropped (§A.6). The call sites that made
  the cache look necessary are repaired regardless. An earlier revision deleted the
  cache outright; that is superseded.
- **D5.** **The offline join never guesses.** A new key is filled only from an
  unambiguous old record; every unresolved entity goes on **the gap list** and is
  regenerated by re-running interpretation, behind a cost estimate the user approves
  before any spend (§B.8).
- **D6.** Every write on `cslh19` requires the user's approval for that specific
  run. Idempotence is not a licence. (The rule exists because on 2026-08-12 at 13:22

  initiative, in answer to a question the user had merely asked about coverage.)
- **D7.** **One dump run, against `AFP-ALL-4`, with `afp_all4_roots.heap.txt` as the
  target list.** Records whose stating theory is not in that image are **not
  pursued**: 19,539 records across 719 theories, the largest block being
  `Geo_Real2`'s 3,349, which is this project's own `MathBench_Prover` work. The user
  made this call knowing that.
- **D8.** **The experience records are migrated** — 6,862 of them (§B.10). They are
  the only population that cannot be regenerated from sources.
- **D9.** The stale `semantics.lmdb.bak-*` directories on `cslh19` are kept. There
  are now **five** (four at 1.7 G plus one at 1.8 G created 2026-08-12 19:04), about
  **8.6 G**, plus `experience_index.lmdb.bak-20260812-190409`.
- **D10.** **Leftovers are pruned, not carried.** Old records no dump entry maps do
  not enter the new store; they are addressable by no process once the fix lands.
  The join reports them by category before the swap, and the pre-swap backup is the

- **D11.** The 5 % acceptance gate of §A.6 is not argued further until there is a

## 1. Glossary

Authoritative for this document; used verbatim in code comments and commit messages,
with no synonyms.

- **universal key** — the byte string addressing an entity in the store.
- **prefix** — the key's first 16 bytes: for a constant/type/class/locale, its
  defining theory's hash; for a theorem-alike entity, the XOR of its constituent
  theories' hashes, with byte 0's LSB then OR'd with their WIP bits. Computed by
  `xor_theory_prefix` (`Isabelle_RPC_Host/universal_key.py:135-143`) on the Python
  side and by `compute_constituents`' fold (`Universal_Key.ML:494-507`) on the ML
  side; **do not write a third implementation.**
- **tail** — `key[16:]`: the 1-byte kind tag plus, for theorem-alike entities, the
  first 15 bytes of the proposition's `Term_Digest.thm128` digest. **The fix changes
  no tail.** This is what makes Part B possible.
- **theorem-alike** — the five kinds whose prefix is an XOR: theorem (`0x02`),
  introduction (`0x12`), elimination (`0x22`), induction (`0x32`), case-split
  (`0x42`) rules.
- **name-addressed** — constant, type, class, locale, theorem collection, method.
  Their keys go through `key_of_ns_entity`, are unaffected by the defect and
  unchanged by the fix.
- **constituent theory** — a theory declaring some constant or type constructor
  occurring in a proposition. Not the theory that states the fact.
- **stating theory** — the theory that states a fact. **Only the dump knows it
  reliably**: a record's name is qualified by the stating theory's *base* name, and
  40 % of the unreached population (101,854 of 255,329 records, over 430 base names)
  carries a base name that two or more image theories share. Every use of a stating
  theory in Part B must come from the dump's long name, never from a record name's
  leading qualifier. Where §B.0 nevertheless attributes records by base name, it
  says so and states the error bar.
- **defining theory** of a constant or type constructor — the theory whose
  `Name_Space` entry declares it. What the current code guesses wrongly.
- **base name / long name** — `Expr` versus `JinjaThreads.Expr`. Base names are not
  unique: 1,652 of the image's 10,614 theories share one, over 608 distinct
  collisions. (The bug report's "1,655 of 10,647" counts a live session 33 theories
  larger than the heap list; both are `AFP-ALL-4`, in different senses.)
- **the entity dump** — Part B step 1: a sweep that enumerates every entity with the
  repaired code and writes what §B.3 specifies to a scratch LMDB. It writes nothing
  to the store.
- **the offline join** — Part B step 2: a Python pass reading the old store plus the
  dump and writing the new store.
- **the gap list** — the join's second output: every new key it could not fill, with
  the **long** stating theory name, entity name and kind, so interpretation can
  regenerate it.

# Part A — the code fix

### A.1 What is wrong, in one paragraph

`Universal_Key.compute_constituents` (`Universal_Key.ML:469`) takes a constant's
defining theory to be the **leading qualifier** of its internal name
(`theory_short_of`, `:464`) — a theory **base name** — and resolves that base name
through `Theory_Hash.hash_of_short` (`theory_hash.ML:225`), whose memo is
**process-global, keyed on the bare base name, never invalidated, and discards its
`context` argument on a hit**. The first theory to claim a base name in a process
claims it for every later computation in that process.

### A.2 The change: ask the name space, not the name

The defining theory has an exact source that `key_of_ns_entity`
(`Universal_Key.ML:558`) already uses: the entity's `Name_Space` entry's
`#theory_long_name`, which is a **long** name. `compute_constituents`' `add` splits
into a constant branch and a type-constructor branch, each consulting its own name
space:

```sml
fun compute_constituents (context : Context.generic) (prop : term) =
  let
    val const_space =
      Consts.space_of (Context.cases Sign.consts_of Proof_Context.consts_of context)
    val type_space = Context.cases Sign.type_space Proof_Context.type_space context

    (* Constituent theories keyed by LONG name.  The defining theory comes from the
       name-space entry -- the same source key_of_ns_entity uses -- never from the
       name's leading qualifier, which is a theory BASE name shared by 1,652 of the
       image's 10,614 theories. *)
    val thys : constituent Strhashtab.table = Strhashtab.empty 16
    (* One `seen` table PER NAME SPACE: a constant and a type constructor can carry
       the same internal name (4 such in HOL-Library.Multiset), and one shared table
       would look up only whichever came first. *)
    val seen_const : unit Strhashtab.table = Strhashtab.empty 32
    val seen_type  : unit Strhashtab.table = Strhashtab.empty 32
    val skipped = Unsynchronized.ref 0

    fun add seen space name =
      if Strhashtab.defined seen name then ()
      else
        (Strhashtab.update seen (name, ());
         case try (Name_Space.the_entry space) name of
           NONE => skipped := !skipped + 1          (* §A.4 *)
         | SOME entry =>
             let val long = default_thy_long_name context (#theory_long_name entry) in
               if Strhashtab.defined thys long then ()
               else Strhashtab.update thys (long, (long, Theory_Hash.hash_of_long context long))
             end)

    fun walk_typ (Term.Type (c, Ts)) = (add seen_type type_space c; List.app walk_typ Ts)
      | walk_typ _ = ()
    fun walk (Const (c, T)) = (add seen_const const_space c; walk_typ T)
      | ...
```

`try (Name_Space.the_entry space)` rather than a `Name_Space.declared` guard followed
by `the_entry`: both are `Change_Table` lookups on the same table
(`name_space.ML:572`, `:255`), so the guard doubles the common case. The one-lookup
idiom already exists at `contrib/Semantic_Embedding/Tools/semantic_digest.ML:277-278`,
as a thunk around the whole projection. Measured saving 0.12 µs per name, about 7 %
of the fix's own cost — worth doing, not a hot-loop hazard.

`default_thy_long_name` (`Universal_Key.ML:418`) is reused as-is for the empty theory
name a proof-local entry carries.

The XOR fold, the WIP-bit OR and the sort at `:494-511` are untouched, and the
provenance list keeps its `(long name, hash)` shape — the record format does not
change.

**What the repaired key is a function of — SETTLED.** Two theories sharing a base name
cannot both be in one cone: `Context.eq_thy_consistent`
(`Isabelle2025-2/src/Pure/context.ML:380-391`) raises
`THEORY ("Duplicate theory name", …)` when two ancestors share a base name, and
`begin_thy` applies it through `merge_ancestors` and `extend_ancestors` (`:534-535`). So
**within any cone a theory base name is unique by construction**, enforced by `Context`
before any `Name_Space` duplicate error is reached. The repaired key is a function of the
proposition and the cone, and the only residual hazard is *cross-cone sharing inside one
process* — which is what §A.6 handles. Cite `eq_thy_consistent` in the signature comment.

An earlier draft asserted instead that a cone containing both
`Optics.Lens_Laws` and `Clean.Lens_Laws` holds exactly one entry for
`Lens_Laws.lens_get`, because `Name_Space.declare` overwrites duplicates. **That is
wrong.** `update_entry` (`name_space.ML:127-130`) overwrites only when
`strict = false`, and the paths that matter pass `strict = true` (`consts.ML:290`,
`:341`; `type.ML:623`, `:668`), raising `err_dup_entry`. The conclusion it reached — that
such a cone cannot exist — is right; the mechanism it named is not.

### A.3 Long name to theory: `Thy_Info.lookup_theory`, not `Theory.check`

`Theory_Hash.hash_of` needs a `theory` value. `Theory_Hash.resolve_theory` ends in
`Context.get_theory` (`Isabelle2025-2/src/Pure/context.ML:353`), a `find_first`
**linear scan over `ancestors_of thy`**; an AFP theory has hundreds to thousands of
ancestors and the sweep resolves several constituents per proposition over more than
a million propositions. The only reason the current code is fast is the memo that is
the bug.

`Thy_Info.lookup_theory : string -> theory option`
(`Isabelle2025-2/src/Pure/Thy/thy_info.ML:141`) is a `Symtab` lookup in Isabelle's own
registry of loaded theories — not a cache of ours, and updated by Isabelle when a
theory is loaded or reloaded. A theory under construction is not in it, hence the
fallback:

```sml
fun hash_of_long context long =
  hash_of (case Thy_Info.lookup_theory long of
             SOME thy => thy
           | NONE => resolve_theory context long)
```

**Why the two routes cannot disagree on the hash**, recorded so it is not re-raised:
`key_of_ns_entity` keeps using `resolve_theory`, so in a live session a long name can
resolve to a different `theory` *value* than `Thy_Info` holds. That produces no key
divergence, because `hash_of` is content-addressed — the branch is chosen by
`Resources.loaded_theory` on the **name** (`theory_hash.ML:147`), the persistent hash
is xxhash128 of the file at `get_theory_path` plus the parents' hashes (`:122-130`,
`:175`), and the WIP hash is FNV of the name. A measurement over `Main`'s 99-theory
cone found the two routes returning the same `Context.theory_identifier` 99/99, but
that measurement's script no longer exists — **re-run it as part of §A.9.** **Do not
"fix" this by routing `key_of_ns_entity` through `hash_of_long`**: that would make it
prefer the heap-registered theory over the in-flight one, a regression in exactly the
editing case `resolve_theory` gets right.

`resolve_theory` infers long-vs-short by `String.isSubstring "."`
(`theory_hash.ML:42-51`), so the dotless global theories — `Pure`, `Main`,
`Complex_Main`, `ML_Bootstrap`, plus eight AFP `(global)` names — take the base-name
branch. No wrong resolution follows (no loaded theory shares their base name, and the
path is reached only on a `Thy_Info` miss), but say that rather than claiming
`resolve_theory` "is correct when given a long name".

### A.4 When a name has no name-space entry

`add` skips the name; it contributes nothing to the XOR and nothing to the stored
constituent list. That must not be silent, and **counting it needs a signature
change**: `compute_constituents : Context.generic -> term -> Theory_Hash.hash *
constituent list` (`Universal_Key.ML:190`) has no channel for a count. Add a third
return component, thread it through `thm_constituents` and `build_entries` to the
sweep's log line, and make **"total skipped names = 0"** a gate in its own right.

The gate must be separate because §B.9's prefix check **cannot see a skip**: it
compares the stored list against a prefix computed from that same list, so it is
consistent by construction whether or not names were dropped.

Falling back to the leading qualifier resolved in the context is rejected: a silent
partial revival of the defect is worse than a counted omission.

### A.5 Deletions, and the second copy of the defect

Delete:

- `Universal_Key.theory_short_of` (`:464`).
- `Theory_Hash.hash_of_short` and `by_short_cache` (`theory_hash.ML:217-233`) plus
  the signature line. `compute_constituents` is its only caller repo-wide.

Keep `Theory_Hash.resolve_theory`: `Universal_Key.ML:251` is only the alias binding,
but the real uses are `:566` (`key_of_ns_entity`) and `:573` (`key_of_theory`), plus
`semantic_store.ML:2084` and `Isabelle_RPC/Tools/context.ML:230`, `:1494`.

**In scope, and missed by the first two drafts:**
`contrib/Semantic_Embedding/Tools/semantic_digest.ML:282-283` cites
`Universal_Key.theory_short_of` in a comment **and re-implements the same
leading-qualifier approximation itself**, as a fallback for names absent from their
space. Deleting `theory_short_of` leaves a dangling reference, and the defect's core
approximation otherwise survives the fix in a second place. Decide there whether the
fallback should become the same counted skip as §A.4.

Three repo-root scratch theories (`Scratch_FlatPathVerify.thy:19`,
`Scratch_DryRunVerify.thy:25`, `:43`) also call `resolve_theory`; they are scratch and
need no action beyond not being broken.

### A.6 `constituents_cache` — re-scope it, and repair the call sites

`Universal_Key.constituents_cache` (`:454`) is a process-global memo:

```sml
val constituents_cache : (Theory_Hash.hash * constituent list) Digest_Tab.table
(* key   = Term_Digest.digest128 = Word64.word * Word64.word
   value = (16-byte prefix, sorted (theory long name, 16-byte hash) list)
   guarded by the global constituents_lock; unbounded; never invalidated *)
```

**Today it causes nothing.** `hash_of_short` already makes constituent computation
context-independent, so the cache returns exactly what recomputation would. Its hazard
is entirely forward-looking and materialises the moment §A.2 lands.

**Then it becomes the same defect one level up.** `Term_Digest.thm128` hashes a `Const`
by its internal name *and its type* (`Term_Digest.ML:100-104`), both built from
base-name-qualified internal names, while the cache's value becomes a list of **long**
names — so its key cannot determine its value. Measured, not conjectured:
`Optics/Lens_Laws.thy:13` and `Clean/src/Lens_Laws.thy:24` both declare a
byte-identical `record ('a, 'b) lens = lens_get … lens_put …` under the shared base name
`Lens_Laws`, and the store holds two records named `Lens_Laws.lens.defs(2)` with
identical `kind`, identical `name` and **byte-identical `expr`**, differing in their
constituent theory and their interpretation text.

#### The design: scope the cache to a population with no base-name collision

Rather than delete the cache, bind its scope to the range over which name resolution
cannot change. The `Theory_Data` value is

```sml
datatype T = No_Cache | Cache of {cache: …, claims: string Symtab.table} Synchronized.var
```

— a **shared mutable pair** of the constituents cache and a map **theory base name →
theory long name** recording who has claimed each base name under this cache. Four
rules, and nothing else:

1. **`empty = No_Cache`, and `thm_constituents` bypasses the cache entirely on
   `No_Cache`.** This is not cosmetic. `THEORY_DATA'_ARGS`' `empty` is a *value*,
   evaluated once at functor application (`Isabelle2025-2/src/Pure/context.ML:744-749`,
   `:772-778`), and `get_data` hands that same object to every theory without its own
   entry (`:441-444`). A record-valued default would therefore make **one process-global
   unpartitioned cache shared by all 10,614 theories of a pre-built image** — the
   original defect, reproduced inside the dump. `No_Cache` is what makes "a heap built
   before this code carries no cache" true rather than catastrophically false.
2. **merge reconciles the parents.** If every data-carrying parent yields the *same*
   pair reference, inherit it. Otherwise allocate a fresh pair: empty cache, claims =
   the union of the parents' maps. **Allocate and union only on that branch** — the
   common case must be allocation-free, and a claims map can hold one entry per theory
   begun under the pair, so unconditional unioning would cost a five-figure `Symtab`
   merge per theory begin.

   Merge is the right place: it is where the parents' data is combined, it receives the
   full `(theory * T) list` (`context.ML:410`, called from `merge_data` at `:447-449`,
   `:525`, `:549`), and it runs before the `at_begin` wrappers (`begin_thy` merges at
   `:539`; `Theory.begin_theory` applies wrappers after, `theory.ML:181-190`). The
   objection that merge cannot see parents without data (`map_filter` at `:447`)
   dissolves under rule 1 plus rule 3: every theory begun after this lands has data, and
   the only data-less parents are pre-code heap theories, which carry no claims to lose.

   *Reconciling the parents is all merge can do* — the new theory is not among its
   arguments, so the self-check below cannot move here.
3. **`at_begin` claims, and forks on collision.** On `No_Cache`, allocate a `Cache`.
   Then look up the beginning theory's own base name in the claims map:
   - it maps to **this theory's own long name** → this is a re-application of the hook,
     not a collision. Change nothing and return `NONE`. **This is load-bearing**:
     `Theory.apply_wrappers` re-runs the whole wrapper list until every wrapper returns
     `NONE` (`theory.ML:83` → `perhaps_loop`, `library.ML:334-340`), and a fork must
     `put` and therefore return `SOME`, so without an "it is me" test the hook forks,
     re-runs, forks again, forever — inside a `Synchronized` critical section. A second
     wrapper already forces the extra pass unconditionally: `update_thm_cache` returns
     `SOME` whenever its fact delta is non-empty (`semantic_store.ML:2148`, hooked at
     `:2155`). This is why the claims structure is a **map to the long name** and not a
     set of base names.
   - it maps to a **different** long name → fork:
     `make (filter (fn (_, cs) => not (exists (fn (n, _) => Long_Name.base_name n = b) cs)) (dest t))`,
     plus a copy of the claims map. One pass, no secondary index.
   - it is absent → inherit the pair unchanged.

   Then record `base name ↦ own long name` and return `SOME`.
4. **Do not write the cache when the empty-name fallback fired.** `default_thy_long_name
   context ""` (`Universal_Key.ML:417-419`) records *the reading context's own theory*
   for entities whose `Name_Space` entry carries no theory name — proof-local and
   `global_naming` declarations (`name_space.ML:487`). Two theories with textually
   identical local statements produce the same `thm128` (which hashes only internal names
   and types, `Term_Digest.ML:100-104`) and would otherwise share a cache entry naming
   whichever theory computed it first — **with no base-name collision anywhere, so no
   fork fires and no purge runs**. `compute_constituents` must report whether the
   fallback fired, alongside §A.4's skip count, and `thm_constituents` must not cache
   the result when it did.

**The invariant:** within the population sharing one cache, every theory base name is
claimed by at most one theory. Since an internal name is qualified by its declaring
theory's base name, two members of the population resolve `Lens_Laws.lens_get`
identically. Same reference ⇒ same claims map ⇒ a collision is visible at `at_begin`;
different reference ⇒ no shared entries. Rule 2 is what keeps the third case — a theory
adopting one parent's pair while its cone absorbs another parent's theories — from
opening a hole.

**Why purging is complete.** A cached entry keyed on digest *d* was computed from a
proposition whose internal names are fixed by *d*. If that proposition mentions a
constant declared by some `*.B` in the forking theory's cone, then in the computing cone
the same internal name `B.c` resolved to that cone's `*.B`, so the entry's stored
constituent list names a theory of base name `B` and the filter drops it. Two gaps, both
closed elsewhere: a constant **skipped** in the computing cone (§A.4) names no `*.B` and
survives with a short constituent set — §A.4's "skipped = 0" gate is the second reason
that gate must be enforced; and the empty-name fallback, closed by rule 4.

**Atomicity.** The pair lives behind one `Synchronized.var`, and the membership test, the
fork and the claim all happen inside a single `Synchronized.change_result`. That var must
also become the lock for **all** cache reads and writes, replacing `constituents_lock`
(`Universal_Key.ML:445`) for that purpose — otherwise a fork's `dest` walks a table being
rehashed in place by a concurrent writer holding the *other* lock
(`Performant_Isabelle_ML/library/hash_table.ML:59-60`). `constituents_registry` (`:458`)
stays global and keeps a lock of its own.

**Recorded costs, since they are real and were argued over.** A fork is
O(cache size) — `Hash_Table` has no copy primitive, only `dest`/`make`
(`hash_table.ML:20-47`) — and the AFP has 1,652 − 608 = **1,044** forking theories, each
retaining its filtered copy for as long as its theory value lives. The alternative of
forking to an *empty* cache is O(1), retains nothing, and would make the purge argument
above unnecessary; it was rejected in favour of keeping the surviving entries. The
measured ceiling on what any such cache can save is **9.14 %** of propositions (22,545
theorems over 20,484 distinct digests) at 12.03 µs a hit — about **25 ms** per
image-scale pass.

**An open question.** "Maps to my own long name ⇒ it is me" is what terminates the
wrapper loop, but it also fires when the *same* theory is re-executed after an edit, in
which case the inherited entries were computed against the previous content and its old
hash. For a WIP theory this is harmless — its hash is FNV of the long name and does not
move with content (`theory_hash.ML:191-209`). For a reloaded persistent theory it is
not. No identifier is both stable across the wrapper loop (`Context.theory_identifier`
changes at every `put`) and distinct across reloads, so this needs an answer before the
interactive path can be trusted.

#### What this does and does not cover

`compute_constituents` is reached from three places, with very different frequencies,
and this design covers one of them.

- **`update_thm_cache` at every theory begin and end** (`semantic_store.ML:2117`, hooked
  at `:2155`) computes keys for the *delta* of newly declared facts through
  `process_facts_into_cache`. It is a recurring cost in every session load and every
  interactive session, and it is exactly where `at_begin` fires and the data is live.
  **This is the design's target** — with a caveat nobody has measured: at `at_begin` the
  fact table is the merge of the parents' and `Thm_Cache`'s snapshot is the merge of the
  parents' snapshots (`:905-916`), so `Facts.dest_static false [cached_facts]
  current_facts` (`:2124`) is **empty in the steady state** and the hook returns `NONE`.
  The delta is large only when the parents come from a heap built without `Thm_Cache`, a
  one-shot bulk pass of mostly distinct digests. Which regime the shipping sessions are
  in decides whether the target exists at all. `vtracing_global` (`:2140`) already prints
  the per-update timing and no such measurement exists anywhere in the repository.
- **The dump sweep** (`enumerate_entries`, once per theory) reads *finished* theories out
  of the `AFP-ALL-4` heap, built before this code existed. No `at_begin` fires, every
  theory's data is `No_Cache`, and rule 1 makes `thm_constituents` bypass the cache
  outright. **The sweep gets no cache** — true only because of rule 1; with a
  record-valued default it would get one global unpartitioned cache instead, and the dump
  would reproduce the very defect it exists to repair.

  The sweep therefore runs in the same regime as outright deletion, and **that regime is
  not the +15 % an earlier draft claimed**. The archived benchmark's five paired rounds
  are 362 / 236 / 254 / 354 / 264 ms with the cache and 291 / 327 / 303 / 217 / 308 ms
  without it plus the call-site repair — paired mean **+4.8 ms (+1.6 %)**, per-round
  spread ±90 ms. "264 → 303" paired round 5 against round 3. The measurement cannot
  resolve the difference, and it omits the sweep's dominant per-entity cost:
  `mk_prop_str` alone is 378 µs per entity (`semantic_store.ML:852`), ~9.1 s over 24,049
  entities against the 264 ms simulated. The real regression is well under 1 %.
- **The semantic query path** (`Isabelle_RPC/Tools/context.ML:1521`, `:1311`) computes a
  key per candidate per query with no cache; on a heap-loaded session the data is
  `No_Cache` there too. §A.7 reorders that filter chain instead — not computing beats
  computing and caching. Note that on a query with no name filter, no term pattern and no
  target type all three promoted filters are the identity (`:879-880`, `:927`, `:968`),
  so the reorder saves nothing on that shape; the live candidate set is the rule
  callbacks' Source-1 nets, about 1,127 thms, i.e. a few ms per query either way.

#### The call sites are repaired regardless

`build_entries`' `mk_constituents` (`semantic_store.ML:821-833`) recomputes what key
construction produced eight lines earlier — measured, that redundancy is roughly half of all
`thm_constituents` calls (19,982 removable of 40,700 in one measurement). Repair it whether
or not a cache is present:

- `semantic_store.ML:821-833` — the five thm-carrying branches read
  `Universal_Key.constituents_of uk`, **falling back to computing** on `NONE`. The fallback
  is deliberate: `retag_thm_key` intentionally does not write the registry
  (`Universal_Key.ML:171-178`), and a registry-only read would harden that documented caveat
  into a hard error.
- `semantic_store.ML:947`/`:955` and `:1087`/`:1088` — same substitution; the `uk` is built
  earlier in the same record literal, so the registry entry exists.

`constituents_registry` (`:458`) stays as it is — universal key → constituent list, the one
memo here whose key determines its value, since the key embeds the XOR and the WIP OR of
exactly the list stored.

#### Designs considered and rejected

- **Deleting the cache outright.** Sound, simple, and — on the corrected reading of the
  benchmark above — free within measurement error. Rejected because it gives up
  `update_thm_cache`'s reuse permanently.
- **Forking to an empty cache instead of a filtered copy.** O(1) instead of O(cache
  size), retains nothing, and makes the purge-completeness argument unnecessary
  altogether. Rejected in favour of keeping the surviving entries; the cost of that
  choice is recorded above.
- **One global cache plus an ambiguity check per entry.** Keep a process-wide
  `base name → long name` `Symtab`, mark a base name ambiguous the second time it is
  claimed, and on a cache hit accept it only if none of the stored constituent long
  names has an ambiguous base name — 2–5 `Symtab` lookups, no name-space re-resolution,
  skipped entirely while the ambiguous set is empty. Strictly less machinery than a
  `Theory_Data` slot plus merge plus fork. Rejected in favour of the design above.
- **A cache passed explicitly per invocation**, using the `thm_uk_cache option` parameter
  that `key_of` and `key_of_theorem'` already carry and that every call site already
  passes as `NONE`. Sound by construction — one invocation, one context, one cone — and
  three lines: `new_thm_uk_cache ()` inside `update_thm_cache` with `SOME c` at `:947`,
  and the same at the top of `enumerate_entries`. **Not adopted, but it remains the
  fallback if the design above misses its gate**, and it is the only option that would
  also serve the sweep.
- **Keying by `(theory identifier of the context, digest)`** — sound, worst hit rate
  measured (65.4 % vs 78.2 %, on a synthetic call sequence that double-lists every entity
  and therefore measures redundancy the call-site repair removes anyway), still takes the
  global lock, grows without bound in interactive use.
- **A global cache with validated hits** (store the constant names, re-resolve on a hit)
  — sound, but validation costs 5.4 µs of a 14.9 µs miss and still holds the global lock.

#### Acceptance criterion

1. **Batch.** One fixed cone, same machine, same `-o threads=N`, the existing enumeration
   path before and after. Accept if elapsed rises by less than 5 %. The sweep gets no
   cache under this design, so this measures the name-space route plus the call-site
   repair.
2. **Interactive.** One theorem-query timing, because §A.7 changes that path too.
3. **Theory begin.** A traced session load, comparing `update_thm_cache`'s own
   `vtracing_global` totals before and after — the number this design exists to improve,
   and the one nobody has. Read two things off the trace: how many `Thm_Cache updated`
   lines carry a non-zero count (which regime the session is in), and their summed
   milliseconds.
4. **Work volume.** Instrument `compute_constituents` with a call counter for one theory
   and assert `calls ≤ theorem entities + rule entities` — one walk per entity, not two.
5. **Fork behaviour.** In the §A.9 fixture, two same-base-name theories in one process:
   the second must fork; the filtered copy must retain exactly the entries that name no
   theory of the colliding base name; the two theories must produce different keys for
   their analogous facts; and the hook must terminate — assert it is applied more than
   once (`update_thm_cache` forces that) and returns `NONE` on the later passes.
6. **No cache on a pre-built heap.** Assert that a theory loaded from the `AFP-ALL-4`
   image reads `No_Cache`, so the dump provably runs uncached.

**What the existing benchmarks do and do not say.** They ran against a **stubbed**
`Theory_Hash.hash_of` on HOL-scale populations, and the code benchmarked as "post-fix" is
**not** §A.2's code (`Meas/measure2.ML:96-118` uses one shared name table and a
const-then-type fallback, not two per-space `seen` tables). Their call sequence
double-lists every static and rule entity and triple-lists dynamic members
(`Meas/measure.ML:55-62`), so the hit rates they report measure the redundancy the
call-site repair removes rather than genuine reuse; the genuine duplicate-proposition
rate is 9.14 %. The one cost they do bound is the name-space route itself:
`compute_constituents` 0.078 s → 0.124 s over 8,316 propositions, **+59 %** (~5.5 µs per
proposition, ~6 s across a 1.1 M-proposition sweep). Per D11 the gate is not re-argued
until there is a real measurement. The archives are at `~/archive/claude-scratchpad/`.

### B.1 The shared tails, and why the join must not guess

**1,156,153** theorem-alike records including WIP (persistent only: 1,133,194) sit on
**1,144,815** distinct tails (persistent: 1,123,391). **10,715 tails are shared by
more than one record, covering 22,053 records** — 10,113 tails by 2 records, 581 by 3,
21 by 4. Persistent only: 9,180 tails, 18,983 records.

An earlier draft claimed these were verbatim AFP copies whose content was
interchangeable, so the join could copy freely. **That is false and was disproved
directly.** The two records named `Lens_Laws.lens.defs(2)` have identical `kind`,
identical `name` and byte-identical `expr` — and **different interpretation text**.

see that; the 22,053 shared-tail records are the pairs that *survived*, not the ones

- the **hit-shortfall gate** (`:1907-1913`, raised at `:1933-1937`) is *meaningless* for

### B.6 Step 2 — the matching rule

Run in two phases. **Phase 1 builds the whole map before anything is written**, because
the decisive ambiguity is only visible globally.

**Phase 1, for every dump entry:**

1. **Name-addressed keys are unchanged.** Assert it — every such key must already exist
   in the old store or be a genuinely new entity — and mark it for verbatim copy. A
   violation means Part A broke something it should not have touched; stop.
2. **Theorem-alike:** collect candidates. First the exact new key if the old store has
   it; otherwise the old records sharing the new key's **tail**.
3. Record the claim: `new key → {candidate old keys}`.

**Phase 2 decides, with the whole map in hand:**

- An old record claimed by **more than one** new key is **not a fill source at all**.
  Every claimant goes on the gap list. This is the rule that catches the defect's own
  signature case, and an exact-key hit is **not** exempt from it: when the memo pinned
  `Optics`, the *Clean* fact's buggy old key is byte-identical to the *Optics* fact's
  correct new key, so the winner takes the exact-hit path while the loser takes the tail
  path, and both would otherwise be filled from one record holding one fact's text.
- A new key with exactly one candidate, claimed by no one else, is filled from it.
- A new key with several candidates is filled only if the **position discriminator**
  identifies one: the old record's stored position file equals the dump's
  `File.symbolic_path (get_theory_path thy)` for the theory being enumerated. Compare
  the recorded strings; never reconstruct a path from a name, and never compare base
  names. A position whose file is a `.ML` file never discriminates, and 269,488 records
  have no position at all — so this saves money, it does not carry correctness.
- **Tombstones are an ambiguity signal, not a non-entity.** If any old key on a tail
  holds a tombstone, no new key on that tail may be filled by tail match; all go on the
  gap list. (Excluding tombstones from the candidate set is what would make the
  surviving sibling *unique* and resurrect a deliberately deleted fact.) An exact hit on
  a tombstone is carried as a tombstone. Note: the store currently contains **zero**
  tombstones — this is defence in depth, and an earlier claim that 724 of them explained
  a vector-count excess was wrong; that excess is the 723 sixteen-byte theory
  embed-status keys.
- **Anything else: do not guess.** No entry is written for the new key — *no entry*, not
  an empty value, since `b""` is the deletion marker (`semantics.py:79`) and would
  permanently shadow the key in any future system layer. The entity goes on the gap list
  with its long stating theory, name and kind.

**In every filled case** the record takes the dump's `name`, the dump's **entity
position** and the dump's **corrected constituents**; `interpretation` and the remaining
fields come from the one chosen old record. For `expr`: compare the dump's proposition
against the old record's `expr` at join time; where they differ, carry the dump's, drop
that key's vector deliberately, and **count the divergences** — a high count on
supposedly-unambiguous fills is itself evidence that the one-to-one rule is leaking.
(Otherwise the first post-migration collection run does this silently:
`semantic_interpretation.py:1078-1079` rewrites `expr` on a cache hit and `update_expr`
invalidates the vector, `semantics.py:660-676`.)

**Legacy shapes.** 38,650 never-reached records have 6, 7 or 8 fields (§B.0). Classify
by length before touching field 5; a 6- or 7-field record has no `theory_constituents`
and cannot be tail-joined on stored provenance.

**Leftovers** — old records no dump entry maps — are **pruned** (D10), counted by
category, and listed in the run report.

**Theory-status records and the counter** (keys ≤ 16 bytes) are copied — their keys are
real theory hashes, unaffected — with one edit, addressed **only by the 16-byte hash the
dump emitted**:

- a theory **in the target list** with gap-list entries: **clear `finished`**, keep the
  cost and token fields. This is what makes the gap list runnable, since
  `plan_interpretation` (`semantic_store.ML:1947-1948`) filters the cone on
  `is_thy_interpreted` (`semantics.py:717`, flag read at `:740`) and a plain re-run
  would report nothing to do.
- a theory **outside the dump's cone**: **leave `finished` alone.** D7 abandoned those
  records and D10 prunes them; clearing the flag would silently arm a full-price
  re-interpretation of the whole theory the next time anyone collects it — 3,349
  entities for `Geo_Real2` alone — outside the metered, approved spend of §B.8.

**Vectors.** One decision per new key: the record and the vector come from the **same**
chosen old key, driven by the explicit `new key → the one old key used` map — never
independently, because the vector-layer self-sufficiency invariant deliberately removed
the read-side backstop (`semantic_embedding.py:1306`). A new key with no source gets **no
vector**. The **16-byte theory embed-status records in each vector store are copied
verbatim** — losing them makes `is_thy_embedded` false across the board and discards the
`total_tokens` ledger (`semantics.py:1199-1201`).

### B.7 Verification gates, before any swap

Reported either way; the join refuses to promote a store that fails one.

- **Dump completeness**: the dump's theory set equals the target list.
- **One-to-one**: the count of old records that fed more than one new key is **zero**.
  Not reported — required.
- **Partition**: every old entity record is in exactly one category — fill source (with
  the one new key it fed), pruned leftover, or carried tombstone — and every new key has
  either exactly one source or a gap-list entry. Reported as counts per category, not as
  a single balancing equation.
- **No lost interpretation**: no old record's interpretation disappears without either
  feeding a new key or being deliberately pruned as a leftover.
- **Prefix check**: for every theorem-alike record in the new store,
  `xor_theory_prefix([h for _, h in rec.theory_constituents]) == key[:16]`. Reuse
  `check_consistency`'s scan (`semantics.py:893-930`); do not re-implement the fold.
  Note it must tolerate the 23,052 XOR-prefixed WIP records.
- **Skipped names** (§A.4) total zero across the dump.
- **No stray empty values**: no zero-length value in the new store except those copied
  from old tombstones.
- **Position coverage** per kind. Expect roughly **228,700** of the previously
  unreachable records to gain positions (memo-signature plus absent-base, §B.0), with a
  residue of about **5,100** — the never-swept and drift populations — which is correct,
  not a failure. Only a residue materially above that is a stop condition. (An earlier
  draft's 229,267 was the bug report's pre-revision figure and would have mis-set this
  gate.)
- **Vectors**: every old vector key has at least one image, and no new key that had a
  vector loses it. Not a count-preservation check — fan-out raises the count and
  drift-collapse lowers it.
- **Experience count** matches §B.10's own reconciliation.

### B.8 The gap list, and what filling it costs

Group the gap list by **long** stating theory and run collection over those theories.
`interpret_file` splits entries into cached and uncached (`semantic_interpretation.py:1083-1084`)
and asks the LLM only about the uncached (gated at `:1123`); its dry run reports how
many need interpretation without spending (`:1090-1093`). Clearing `finished` on exactly
the gap theories (§B.6) is what lets `plan_interpretation` see them, and the cache filter
keys on the entity's universal key — the same key the join wrote — so records already
filled are not re-paid for.

**The cost is driven by the theory count, not the entity count.** `_BATCH_SIZE = 20`
(`semantic_interpretation.py:118`) and each batch re-sends the theory's context, so a
theory with three gap entries still pays one full batch (~$0.40 at the recorded
uncached-input rate). From the only per-entity figures the repo records
(`INTERPRETATION_CODEX_DRIVER_PLAN.md:716-720`): `Codex.gpt-5.6-sol` did 244 entities for
$1.7736 ($0.0073 each), `ClaudeCode.claude-opus-4-8[1m]` 36 for $0.3733 ($0.0104 each).
So 20,000 gap entries cost **$145–210 if dense** and **$1,000–1,200 if spread over ~3,000
theories**. The gap list is by construction thin and wide.

Therefore the join must report **the gap list's theory count alongside its entity
count**, and the estimate presented to the user is
`(entities × marginal rate) + (theories × one-batch fixed cost)`. The existing dry run
returns a count, not money (`semantic_interpretation.py:1093`, rendered at
`semantics.py:1582-1594`); compute the dollar figure in the migration script from the
recorded per-theory `cost_usd`/token ledger. **Do not present the raw count as a cost
estimate.**

Sequence: **dump → join → the join's own count and estimate → the user approves →
`collect` over the gap theories → chained embed.**

### B.9 Promotion, and getting back

Build into `semantics.lmdb.building`; rename to `semantics.lmdb.new` **only after every
§B.7 gate passes**; the swap refuses a bare `.building`. This mirrors
`install_system_db`'s temp-dir-then-rename with crash heal
(`snapshot_sync.py:584-650`).

Then, with §B.2 item 2 verified, move the old directories to `.bak-<timestamp>` and the
new ones into place — **all four environments together**, including
`experience_index.lmdb`, which otherwise survives the swap pointing at pre-migration
experience keys and makes every experience silently unavailable to AoA
(`_experience_hits` drops candidates whose `Semantic_DB[uk]` is `None`,
`semantics.py:1917-1919`). Run `rebuild_experience_index` before the store is exercised.

Rollback is the same moves reversed, using the §B.2 backup rather than a renamed live
directory. Keep the dump until the new store has been exercised.

Note for anyone merging afterwards: `merge_snapshot.py:218-223` aborts when a migrated
snapshot meets a locally-collected pre-migration store, and its message names the wrong
cause.

### B.10 The experience migration (D8)

**6,862 records**, 6,769 persistent and 93 WIP; all are 8-field. A separate pass:
experiences are agent-written, never enumerated from a theory, so the dump never sees
them and §B.4's cone is irrelevant to them.

Their keys are built by `Universal_Key.compute_constituents` over the goal patterns
(`Isabelle_RPC/Tools/context.ML:1089-1091`), so the fix moves them. Worse than for
theorem records, the stored constituent list is **also the availability predicate** at
retrieval time — `all(h in loaded for _, h in rec.theory_constituents)`
(`semantics.py:1917-1922`), with `Experience_Index.candidates` bucketed on the same
hashes — so a wrongly-resolved entry silently withholds the experience from every proof
that does not load the misnamed theory. **That damage exists today**: 71 records (65
persistent, 6 WIP) name a constituent long name the reached population never resolves
to, spread over 11 theories (`Berlekamp_Zassenhaus.Unique_Factorization_Poly` 13,
`HOL-Algebra.FiniteProduct` 12, `Triangle.Angles` 11, `HOL-Library.Interval` 10, and
seven more). That is 1.0 %, and it is a lower bound — a record that stored the *winner*
while its patterns needed the loser looks clean to the test.

**The pass is circular unless the context is named explicitly, and that must be
confronted rather than coded around.** Recomputing an experience's constituents means
re-parsing its stored `goal_patterns`, which needs a context; the only thing on the
record that names any theory is `theory_constituents` — the field being repaired.
`experience_constituents` (`context.ML:1085-1087`) also **raises** if any pattern fails
to parse, and its only caller passes an AoA proof-state context
(`mcp_http_server.py:2279-2285`).

What makes it tractable: the key's **tail** is
`xxhash128(name\0patterns\0desc\0experience)[:15]` (`mcp_http_server.py:2301-2306`) —
pure record content, recomputable offline. **Only the 16-byte prefix needs a context.**

So: add a `static_context_unpacker`-based variant of the `Experience.constituents`
callback; build the context by merging the theories the *old* constituent list names;
and treat **any pattern that fails to parse, or whose recomputed constituent set names a
theory outside that merge, as a refusal to be reported for the user to adjudicate — never
a silent skip.** Move the key, then `Experience_Index.rebuild` (the index holds 405
16-byte keys, not one per experience). Also record the writing context's theory long
names on the record at write time, so the next migration is not circular.

`write_memory`'s docstring claims content-addressed idempotency
(`mcp_http_server.py:2242-2244`); after the fix a byte-identical re-write lands on a
different key from a pre-fix record, leaving only the 0.7-cosine dedup heuristic
(`:2371-2393`) between that and a duplicated corpus. Fix the docstring.

**Concurrency.** 6,682 of these were written on the afternoon of 2026-08-12, so the store
is a live target. Anything written between the join's read and the swap is lost. Confirm
at run time that the writer is stopped — do not infer it from this sentence.

### B.11 What downstream users lose, for the release note

Recorded because D3 writes it off. After the release a user's own locally collected
records stay under old keys and become unaddressable; the shipped AFP corpus is
unaffected, because the system DB is re-keyed with it. Retrieval does **not** fail
loudly: `topk` drops keys with no vector and the non-reranker path materialises
placeholder records carrying a name and no interpretation
(`semantics.py:2053-2062`), so the result looks like an answer. The remedy is to re-run
collection over one's own theories with **`--reinterpret`**
(`isabelle_semantics.py:1511`); a plain `collect` reports nothing to do, because the
theory-status records are keyed by theory hash and still say `finished`. AoA experience
memories cannot be regenerated this way at all.

# Part F — review record

Three adversarial rounds: five reviewers by lens, then three refuters, then a narrower
pair over the parts rewritten in between (the join mechanism, and every number).
Findings were folded into the text above. Recorded here so they are not raised again:

**Refuted outright.**

- *`Cannot_Hash` newly exposed by the fix.* False premise: `enumerate_entries`
  (`semantic_store.ML:1589`) and `backfill_theory` (`:1867`) already call `hash_of` on
  every theory in the cone, and `hash_of` recurses over all parents, so every "losing
  sibling" is already hashed today.
- *`Thy_Info` staleness flipping the WIP bit and misleading `clean_wip`.* The
  WIP/persistent branch is chosen by `Resources.loaded_theory` on the long **name**
  (`theory_hash.ML:147`), so two theory values sharing a name always agree on the LSB.
- *No stop-then-start sequence for the REPL.* §B.2 already requires it.
- *The two performance measurements were one measurement reported twice.* Different
  populations, different metrics. The real error was claiming they "agreed" on a figure
  only one produced.

**Withdrawn by the user, correctly.** The first round treated "Part A ships without
Part B" as the headline risk and built a key-scheme marker, a `SCHEMA_VERSION` bump, a CI
gate and a publication freeze on top of it. That scenario does not arise (D3).

**Verified in the third round and worth not re-deriving:** the gap list *is* runnable and
clearing `finished` does not re-pay for already-filled records (the cache filter keys on
the entity's universal key, `semantic_interpretation.py:898`, and persistent records send
`semantic_digest = NONE, deps = []`, `semantic_store.ML:1589-1593`, so no staleness test
can fire); a cleared theory re-enumerates only its own entities, not its cone
(`theory_structure.ML:179`, `:198`); the dry run can be scoped to just the gap theories;
copying the vector stores' 16-byte embed-status records verbatim does not starve the new
keys, because the chained embed is a whole-DB scan (`Tools/interpret_command.ML:106`); and
a persistent status record that loses `finished` is not mistaken for a WIP one
(`semantics.py:735-740`).
