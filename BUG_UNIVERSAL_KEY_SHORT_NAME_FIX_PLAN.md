# Fix plan for BUG_UNIVERSAL_KEY_SHORT_NAME

Status: **reviewed (two rounds, adversarial), revised, nothing implemented.**
Drafted 2026-08-12, revised the same day after review.

Two halves, in order:

- **Part A** repairs the key computation in `contrib/Isabelle_RPC`, so a theorem's
  universal key stops depending on the order in which theories were resolved in
  the ML process.
- **Part B** rebuilds the semantic store on `cslh19` under the repaired keys,
  recovering what can be recovered and listing what cannot, so it can be
  regenerated deliberately.

The defect is diagnosed in `BUG_UNIVERSAL_KEY_SHORT_NAME.md`; that document is
the evidence, this one is the response. The position work that surfaced it is
`contrib/Semantic_Embedding/ENTITY_POSITION_PLAN.md` (§18 records the sweep whose
17 % shortfall started this).

## 0. Decisions already taken

From the user; not open for review, recorded so the plan's assumptions are visible.

- **D1.** The rescue builds a **new store** and swaps whole directories at the
  end. It never mutates the existing store in place.
- **D2.** The rescue runs **on `cslh19`** — the store and the `AFP-ALL-4` session
  image are there and nowhere else.
- **D3.** Scope is **our own data**. Part A is followed immediately by Part B and
  only then by a release, so the "Part A shipped alone" scenario does not arise
  and is not defended against: no key-scheme marker, no `SCHEMA_VERSION` bump, no
  CI key-provenance gate, no publication freeze. **Downstream users' own
  user-layer records are written off** — after the release their locally
  collected theories will be unaddressable, and recovering them is not this
  plan's job. §B.9 records what that costs them, for the release note.
- **D4.** `Universal_Key.constituents_cache` is **deleted**, and the call sites
  that made it look necessary are repaired (§A.6).
- **D5.** **The offline join never guesses.** A new key is filled only when the
  old record is unambiguous; every unresolved key goes on **the gap list** and is
  regenerated by re-running interpretation, behind a dry-run cost estimate the
  user approves before any spend (§B.5).
- **D6.** Every write on `cslh19` requires the user's approval for that specific
  run. Idempotence is not a licence. (This rule exists because on 2026-08-12 at
  13:22 this assistant launched a write pass to the production store on its own
  initiative, in answer to a question the user had merely asked about coverage.)
- **D7.** **One dump run, against `AFP-ALL-4`, with `afp_all4_roots.heap.txt` as
  the target list.** Records whose stating theory is not in that image are **not
  pursued** — no second run against another session's heap image. This abandons
  about 19,539 records across 719 theories, the largest single block being
  `Geo_Real2`'s 3,349, which is this project's own `MathBench_Prover` work. The
  user made this call knowing that.
- **D8.** **The experience records are migrated.** There are **6,862** of them,
  not the 180 an earlier scan found — 6,682 persistent ones were written on
  2026-08-12 between 13:34 and 19:04. They are the only population in the store
  that cannot be regenerated from sources, and their keys go through
  `compute_constituents`, so the fix moves them. Migration is a separate pass
  (§B.10), independent of the dump's coverage: experiences are agent-written, not
  enumerated from any theory.
- **D9.** The four stale `bak-2026081*` backup directories on `cslh19` are kept.
- **D10.** **Leftovers are pruned, not carried.** Old records that no dump entry
  maps — roughly 20,000, dominated by the 19,539 of D7 — do not enter the new
  store. They are addressable by no process once the fix lands, so carrying them
  would only preserve the illusion that the store still holds them. The join
  reports them by category before the swap, and the pre-swap backup remains the
  record of what was dropped.

## 1. Glossary

Authoritative for this document; used verbatim in code comments and commit
messages, with no synonyms.

- **universal key** — the byte string addressing an entity in the store.
- **prefix** — the key's first 16 bytes: for a constant/type/class/locale, its
  defining theory's hash; for a theorem-alike entity, the XOR of its constituent
  theories' hashes, with byte 0's LSB then OR'd with their WIP bits.
- **tail** — `key[16:]`: the 1-byte kind tag plus, for theorem-alike entities,
  the first 15 bytes of the proposition's `Term_Digest.thm128` digest. **The fix
  changes no tail.** This is what makes Part B possible.
- **theorem-alike** — the five kinds whose prefix is an XOR: theorem (`0x02`),
  introduction (`0x12`), elimination (`0x22`), induction (`0x32`), case-split
  (`0x42`) rules.
- **name-addressed** — constant, type, class, locale, theorem collection, method.
  Their keys go through `key_of_ns_entity`, are unaffected by the defect and
  unchanged by the fix.
- **constituent theory** — a theory declaring some constant or type constructor
  occurring in a proposition. Not the theory that states the fact.
- **stating theory** — the theory that states a fact. Recoverable from a record's
  name, whose leading qualifier is the stating theory's base name. Distinct from
  every constituent theory, and the distinction matters: §B.0's residue is
  explained by it.
- **defining theory** of a constant or type constructor — the theory whose
  `Name_Space` entry declares it. What the current code guesses wrongly.
- **base name / long name** — `Expr` versus `JinjaThreads.Expr`. Base names are
  not unique: 1,655 of `AFP-ALL-4`'s 10,647 loaded theories share one.
- **the entity dump** — Part B step 1: a sweep that enumerates every entity with
  the repaired code and writes `(new universal key, entity position, corrected
  constituents, name, kind)` to a scratch LMDB. It writes nothing to the store.
- **the offline join** — Part B step 2: a Python pass reading the old store plus
  the entity dump and writing the new store.
- **the gap list** — the offline join's second output: every new key it could not
  fill, with the stating theory, entity name and kind, so interpretation can
  regenerate it.

# Part A — the code fix

### A.1 What is wrong, in one paragraph

`Universal_Key.compute_constituents` (`Universal_Key.ML:469`) takes a constant's
defining theory to be the **leading qualifier** of its internal name
(`theory_short_of`, `:464`) — a theory **base name** — and resolves that base name
through `Theory_Hash.hash_of_short` (`theory_hash.ML:225`), whose memo is
**process-global, keyed on the bare base name, never invalidated, and discards its
`context` argument on a hit**. The first theory to claim a base name in a process
claims it for every later computation in that process.

### A.2 The change: ask the name space, not the name

The defining theory has an exact source that `key_of_ns_entity`
(`Universal_Key.ML:558`) already uses: the entity's `Name_Space` entry's
`#theory_long_name`, which is a **long** name and unambiguous.
`compute_constituents`' `add` splits into a constant branch and a type-constructor
branch, each consulting its own name space:

```sml
fun compute_constituents (context : Context.generic) (prop : term) =
  let
    val const_space =
      Consts.space_of (Context.cases Sign.consts_of Proof_Context.consts_of context)
    val type_space = Context.cases Sign.type_space Proof_Context.type_space context

    (* Constituent theories keyed by LONG name, which is unique.  The defining
       theory comes from the name-space entry -- the same source key_of_ns_entity
       uses -- never from the name's leading qualifier, which is a theory BASE
       name shared by 1,655 of AFP-ALL-4's 10,647 theories. *)
    val thys : constituent Strhashtab.table = Strhashtab.empty 16
    (* One `seen` table PER NAME SPACE.  A constant and a type constructor can
       carry the same internal name (measured: 4 in HOL-Library.Multiset), and one
       shared table would look up only whichever came first. *)
    val seen_const : unit Strhashtab.table = Strhashtab.empty 32
    val seen_type  : unit Strhashtab.table = Strhashtab.empty 32
    val skipped = Unsynchronized.ref 0

    fun add seen space name =
      if Strhashtab.defined seen name then ()
      else
        (Strhashtab.update seen (name, ());
         case try (Name_Space.the_entry space) name of
           NONE => skipped := !skipped + 1          (* §A.4 *)
         | SOME entry =>
             let val long = default_thy_long_name context (#theory_long_name entry) in
               if Strhashtab.defined thys long then ()
               else Strhashtab.update thys (long, (long, Theory_Hash.hash_of_long context long))
             end)

    fun walk_typ (Term.Type (c, Ts)) = (add seen_type type_space c; List.app walk_typ Ts)
      | walk_typ _ = ()
    fun walk (Const (c, T)) = (add seen_const const_space c; walk_typ T)
      | ...
```

`try (Name_Space.the_entry space)` rather than a `Name_Space.declared` guard
followed by `the_entry`: both are `Change_Table` lookups on the same table
(`name_space.ML:572`, `:255`), so the guard doubles the cost of the common case;
the one-lookup idiom is already used at
`contrib/Semantic_Embedding/Tools/semantic_digest.ML:276`. (Measured: 0.12 µs per
name saved, ~7 % of the fix's own cost — worth doing, not a hot-loop hazard.)

`default_thy_long_name` (`Universal_Key.ML:418`) is reused as-is for the empty
theory name a proof-local entry carries.

The XOR fold, the WIP-bit OR and the sort at `:494-511` are untouched, and the
provenance list keeps its `(long name, hash)` shape — the record format does not
change.

**What the repaired key is a function of.** Not the proposition alone. It is a
function of **the proposition and the context's ancestor cone**, because the
defining theory is read out of that context's name spaces. This is not a
shortcoming to be fixed later; it is forced. An internal name is qualified by its
declaring theory's *base* name, and `Name_Space.declare` overwrites on a duplicate
internal name (`name_space.ML:127-130`, used at `:594`), so a cone containing both
`Optics.Lens_Laws` and `Clean.Lens_Laws` holds exactly **one** entry for
`Lens_Laws.lens_get`. The fix separates those two theories' facts only because the
sweep's per-theory contexts have disjoint ancestor cones — not because the name
space can tell them apart. Say this in the signature comment; do not claim the key
depends on the thm alone.

### A.3 Long name to theory: `Thy_Info.lookup_theory`, not `Theory.check`

`Theory_Hash.hash_of` needs a `theory` value. The obvious route,
`Theory_Hash.resolve_theory`, ends in `Context.get_theory`
(`Isabelle2025-2/src/Pure/context.ML:353`), a `find_first` **linear scan over
`ancestors_of thy`**. An AFP theory has hundreds to thousands of ancestors and the
sweep resolves several constituents per proposition over more than a million
propositions. The only reason the current code is fast is the very memo that is
the bug.

`Thy_Info.lookup_theory : string -> theory option`
(`Isabelle2025-2/src/Pure/Thy/thy_info.ML:141`) is a `Symtab` lookup in Isabelle's
own registry of loaded theories — not a cache of ours, and updated by Isabelle
when a theory is loaded or reloaded. Theories in a session image are in it
(`resolve_roots`, `semantic_interpretation_app.ML:92`, already relies on
`Thy_Info.get_theory`). A theory under construction is not, hence the fallback:

```sml
fun hash_of_long context long =
  hash_of (case Thy_Info.lookup_theory long of
             SOME thy => thy
           | NONE => resolve_theory context long)
```

**Why the two routes cannot disagree on the hash**, recorded here so it is not
re-raised: `key_of_ns_entity` keeps using `resolve_theory`, so in a live session a
long name can resolve to a different `theory` *value* than `Thy_Info` holds. That
produces no key divergence, because `hash_of` is content-addressed — the branch is
chosen by `Resources.loaded_theory` on the **name** (`theory_hash.ML:147`), the
persistent hash is xxhash128 of the file at `get_theory_path` plus the parents'
hashes (`:122-130`, `:175`), and the WIP hash is FNV of the name. All are
functions of the name and master directory. Measured: over `Main`'s 99-theory cone
the two routes return the same `Context.theory_identifier` 99/99. **Do not
"fix" this by routing `key_of_ns_entity` through `hash_of_long`** — that would make
it prefer the heap-registered theory over the in-flight one, a regression in
exactly the editing case `resolve_theory` gets right.

`resolve_theory` infers long-vs-short by `String.isSubstring "."`
(`theory_hash.ML:42-51`), so the dotless global theories — `Pure`, `Main`,
`Complex_Main`, `ML_Bootstrap`, plus eight AFP `(global)` names — take the
base-name branch. No wrong resolution follows (no loaded theory shares their base
name, and the path is reached only on a `Thy_Info` miss), but say that honestly
rather than claiming `resolve_theory` "is correct when given a long name".

### A.4 When a name has no name-space entry

`add` skips the name; it contributes nothing to the XOR and nothing to the stored
constituent list. That must not be silent, and **counting it needs a signature
change**: `compute_constituents : Context.generic -> term -> Theory_Hash.hash *
constituent list` (`Universal_Key.ML:190`) has no channel for a count, so the
per-theory log line cannot report one as the plan previously claimed. Add a third
return component (the skip count), thread it through `thm_constituents` and
`build_entries` to the sweep's log line, and make **"total skipped names = 0"** a
gate in its own right.

The gate has to be separate because §B.6's re-XOR check **cannot see a skip**: it
compares the stored list against a prefix computed from that same list, so it is
consistent by construction whether or not names were dropped.

The alternative — falling back to the leading qualifier resolved in the context —
is rejected: a silent partial revival of the defect is worse than a counted
omission.

### A.5 Deletions

- `Universal_Key.theory_short_of` (`:464`) — its only caller disappears.
- `Theory_Hash.hash_of_short` and `by_short_cache` (`theory_hash.ML:217-233`) plus
  the signature line. Verified by grep: `compute_constituents` is the only caller
  in the repo.
- `Theory_Hash.resolve_theory` **stays** — `Universal_Key.ML:251`,
  `semantic_store.ML:2084` and `context.ML:230,1494` use it.

### A.6 `constituents_cache` — delete it, and repair the call sites

`Universal_Key.constituents_cache` (`:454`) is a second process-global memo:

```sml
val constituents_cache : (Theory_Hash.hash * constituent list) Digest_Tab.table
(* key   = Term_Digest.digest128 = Word64.word * Word64.word
   value = (16-byte prefix, sorted (theory long name, 16-byte hash) list)
   guarded by the global constituents_lock; unbounded; never invalidated *)
```

**Today it causes nothing.** `hash_of_short` already makes constituent computation
context-independent, so the cache returns exactly what recomputation would. Its
hazard is entirely forward-looking and materialises the moment §A.2 lands.

**Then it becomes the same defect one level up.** `Term_Digest.thm128` hashes a
`Const` by its internal name *and its type* (`Term_Digest.ML:100-104`), both built
from base-name-qualified internal names, while the cache's value becomes a list of
**long** names. Its key therefore cannot determine its value. This is measured,
not conjectured: `Optics/Lens_Laws.thy:13` and `Clean/src/Lens_Laws.thy:24` both
declare a byte-identical `record ('a, 'b) lens = lens_get … lens_put …` under the
shared base name `Lens_Laws`, and the store holds two records named
`Lens_Laws.lens.defs(2)` with identical `kind`, identical `name` and **byte-identical
`expr`**, differing only in the constituent theory and the interpretation text.
One digest, two legitimately different long-name constituent sets, one process.

**What stays.** `constituents_registry` (`:458`) — universal key → constituent
list — is the one memo here whose key does determine its value, since the key
embeds the XOR *and the WIP OR* of exactly the list stored. `constituents_lock`
(`:445`) stays, because it still guards that registry (`:529`, `:539`).

**The call sites are part of the deletion.** `build_entries`' `mk_constituents`
(`semantic_store.ML:821-833`) recomputes what key construction produced eight lines
earlier, so a naive deletion nearly doubles the work. Measured over one
enumeration unit, medians of five rounds: **264 ms today, 487 ms if the cache is
simply deleted, 303 ms if it is deleted and `mk_constituents` reads the registry**.
So:

- `semantic_store.ML:821-833` — the five thm-carrying branches read
  `Universal_Key.constituents_of uk`, **falling back to computing** on `NONE`. The
  fallback is deliberate: `retag_thm_key` intentionally does not write the registry
  (`Universal_Key.ML:171-178`), and a registry-only read would harden that
  documented caveat into a hard error.
- `semantic_store.ML:947`/`:955` and `:1087`/`:1088` — same substitution; the `uk`
  is built earlier in the same record literal, so the registry entry exists.

Deleting the cache also removes one `Term_Digest.thm128` call per key build:
`thm_constituents` computes the digest *only* to have a cache key (`:515`), and
`build_thm_key` computes it again for the payload.

**Rejected designs.** Keying by `(theory identifier of the context, digest)` —
sound, but the worst hit rate measured (65.4 % vs 78.2 %), still takes the global
lock, and grows without bound in interactive use. An explicitly-passed cache scoped
to one swept theory — sound, lock-free, retains 90.7 % of the hits, but once the
redundant calls above are gone it is worth roughly four seconds of CPU across an
entire AFP sweep, against a new lifetime to reason about at six call sites.

**What the benchmarks do and do not say.** They were run against a **stubbed**
`Theory_Hash.hash_of` on HOL-scale populations, and the code benchmarked as
"post-fix" is **not** §A.2's code (no per-space `seen` tables, a `try` with a `Pure`
fallback rather than a counted skip, a private Symtab rather than
`Thy_Info.lookup_theory`). Two costs must be reported separately and neither has
been measured on the real thing:

- deleting the cache and repairing the call sites: **264 → 303 ms**, +15 % on this
  micro-benchmark, per-round spread 236–362 and 217–327;
- the name-space route itself: `compute_constituents` **0.078 s → 0.124 s** over
  8,316 propositions, **+59 %** (~5.5 µs per proposition, ~6 s of CPU across a
  1.1 M-proposition sweep).

**On this evidence the change does not pass the acceptance criterion below.** That
is stated plainly rather than argued away: the micro-benchmark measures the
constituent machinery in isolation, which is ~2.8 % of one step of a pipeline whose
per-entity cost is dominated by a 378 µs pretty-print and an LLM call. The gate
must be run on the real cone before the change is accepted.

**Acceptance criterion.**

1. **Batch.** One fixed cone, same machine, same `-o threads=N`, the existing
   enumeration path before and after. Accept if elapsed rises by less than 5 %.
2. **Interactive.** One theorem-query timing, because §A.7 changes that path too.
3. **Work volume.** Instrument `compute_constituents` with a call counter for one
   theory and assert `calls ≤ theorem entities + rule entities` — one walk per
   entity, not two. This is what distinguishes the repaired deletion from the naive
   one, and it is cheap enough to keep as a test.

### A.7 The interactive query path must be reordered in the same commit

`context.ML:1256-1266` calls `Universal_Key.thm_constituents` per live candidate as
the **second** filter in a chain whose own comment two lines above claims
cheap-to-expensive ordering. With the cache gone that call goes from ~0.7 µs to
~14.9 µs per candidate — a ~20× increase on a path the batch gate does not touch.
Move `scope_ok` after `filter_opt`, `prop_matches` and `target_type_filter`, and fix
the comment.

### A.8 Comments that state the false assumption and must go

- `Universal_Key.ML:58-65`: *"A constant/type's defining theory is taken as the
  LEADING QUALIFIER … No name-space lookup is involved, so the key depends only on
  the thm, not on the context it is reached from."* Replace with the name-space
  rule and §A.2's honest statement of the key's domain. Do **not** write that the
  second sentence "becomes true in the only sense that matters" — it does not.
- `Universal_Key.ML:472-473`: *"keyed by short name (unique within a runtime)"*.
- `theory_hash.ML:217-221`: goes with `by_short_cache`.

### A.9 Tests

**There is no Universal_Key test theory today** — `contrib/Isabelle_RPC` holds only
`test_protocol.thy`, `test_callback.ML` and `test_multiplexed.ML`, all wire-protocol
tests. One has to be created, and it needs a **running Isabelle_RPC host**, because
`Theory_Hash.hash_of` RPCs to Python for any loaded theory (`theory_hash.ML:147`,
`:178`).

The regression fixture is cheap and must be specified rather than hand-waved: two
sibling sessions in one ROOT, each containing a `Foo.thy` that declares a constant,
plus a third session importing both by long name, builds in seconds against the
existing `Pure`/`HOL` heaps and gives loaded theories `A.Foo` and `B.Foo` in one
process.

1. **Regression.** With the shared base name pinned to `A.Foo` first, key a
   proposition over `B.Foo`'s constant. Before the fix the two theories' analogous
   facts collide; after it they differ. Must **fail before and pass after** — a test
   that passes both ways proves nothing.
2. **Order independence.** Same theorem, two contexts **with the same ancestor
   set**, resolved in both orders: the key must agree. The ancestor set is held
   fixed deliberately — per §A.2 the key is a function of the proposition *and* the
   cone, so varying the cone is allowed to change the key, and test 1 depends on
   its doing so.
3. **Name-addressed keys unchanged.** A constant/type/class/locale key byte-identical
   before and after. Load-bearing for Part B, which copies those records untouched.
4. **Provenance shape unchanged.** The `(long name, hash)` list still re-XORs — with
   the WIP OR applied — to the key's prefix.
5. **No skipped names.** §A.4's counter is zero over the fixture.

After editing any `.ML`, **restart the REPL**; do not rebuild a heap and do not chase
heap timestamps.

# Part B — the rescue on `cslh19`

### B.0 What we are rescuing, and why the residue is what it is

Two read-only full-store scans plus a log cross-check, run 2026-08-12.

The store held **1,362,343** entity records and 11,469 theory-status/counter
records when scanned at 13:34; by 19:04 it held **1,369,025**, the whole
difference being 6,682 newly written experience records (D8). **Every single
entity record carries an interpretation** — there is no cheap stratum, which is
the whole argument for migrating rather than re-collecting. 1,092,855 records
have an entity position, 13,979 were reached but are legitimately position-less,
and 255,509 were never reached by any sweep. Of those, 233,795 are persistent
theorem-alike records — the population this plan is about. (The bug report's
234,398 is the same population plus 603 name-addressed stragglers.)

Classifying all 233,795 against what the reached population proves about the current
resolution, and cross-checking each record's **stating theory** against the theories
the sweeps actually logged:

- **221,677 (94.8 %)** carry the memo's signature — they name a long name the
  current process never resolves to — **and their stating theory was swept**. These
  are the defect, cleanly.
- 6,783 (2.9 %) name a constituent base name that appears nowhere in the reached
  population. Consistent with the defect, not separately proven.
- 3,873 (1.7 %) have a perfectly reproducible key but their **stating theory was
  never swept**.
- 728 are both memo-signature and never-swept; 79 are both unswept-constituent and
  never-swept.
- 635 (0.3 %) are AFP snapshot drift — a constituent theory's content genuinely
  changed.
- **20 records (0.009 %) have no explanation at all.**

So the defect accounts for 94.8 % directly and up to 97.7 % including the
consistent-but-unproven band; AFP drift accounts for 635; the rest is sweep
coverage. Together, 233,775 of 233,795.

**The coverage population is larger than that 3,873 + 728 + 79 suggests**, because
those counts are restricted to persistent theorem-alike records. Counting every
unreached entity record whose stating theory no sweep ever logged gives **25,542
records across 737 theories**, and it splits cleanly in two:

- **6,003 records across 18 theories whose theory IS in the `AFP-ALL-4` image** and
  was simply absent from the previous sweep's target list — `Example_PIL` 1,476,
  `Example_SOL` 1,129, `Substitution_Lifting_Example` 1,105, `Amortized_Examples`
  842, `Example_Bounded_FOL` 787, and thirteen smaller. Adopting the heap list
  (§B.4) recovers these at no extra cost.
- **19,539 records across 719 theories whose theory is NOT in the image** —
  `Geo_Real2` 3,349 and a long tail of Why3-generated verification-condition
  theories. Per D7 these are abandoned.

Three independent supports for the causal claim, beyond the classification: among
the 899,399 **reached** records, **0 of the 366 contested base names carries more
than one long name** (per-context resolution would put both siblings there); sweep
order predicted the winner 4 for 4 in the earlier per-theory analysis; and one
record's stored constituents name `Clean.Lens_Laws` while its position points at
`$AFP/Optics/Lens_Laws.thy:13`.

One test that did **not** work, recorded so it is not repeated: substituting the
reached population's winner hash into a memo-signature record's constituent list and
looking the resulting key up in the store hits only 5,860 of 222,405. That is the
expected outcome, not counter-evidence — the sweep's key has a record only if some
*collection* run shared its pinning, and collection mostly ran once. The test has no
discriminating power.

### B.1 The shared tails, and why the join must not guess

1,156,153 theorem-alike records (including WIP; the bug report's 1,134,149 excludes
them) sit on 1,144,815 distinct tails. **10,715 tails are shared by more than one
record, covering 22,053 records — 1.9 %.**

An earlier draft claimed these were verbatim AFP copies whose content was
interchangeable, so the join could copy freely. **That is false and was disproved
directly.** The two records named `Lens_Laws.lens.defs(2)` have identical `kind`,
identical `name` and byte-identical `expr` — and **different interpretation text**.
Nor are the source theories verbatim copies: `Clean/src/Lens_Laws.thy` is a 331-line
excerpt of `Optics/Lens_Laws.thy`'s 484 lines, with different imports and missing
definitions. And the flagship example of the *other* reading was also wrong:
`LambdaAuth/Syntax.thy` declares no `b_raw` at all, so that row is the defect's
damage, not a second genuine fact. A shared-tail group can be either, and the stored
fields cannot tell them apart — `name` and `expr` agree in both cases.

Hence **D5: the join never guesses.** The consequence is that no tie-break heuristic
carries correctness, which in turn dissolves three review findings rather than
patching them (the fan-out copying the wrong fact's `name`/`expr`/`interpretation`;
the record and the vector being chosen from different old keys; the reconciliation
gate being true by construction).

### B.2 Preconditions

1. **The user's approval for this specific run** (D6), for every write anywhere on
   `cslh19` — including the scratch dump and the derived
   `Isabelle_Theory_Hash/theory_hash.lmdb` that `resolve_roots` writes via
   `store_theory_hash` (`theory_hash.ML:235-240`). That one is a rebuildable
   hash→name cache and needs no backup; it is named here only so "any write" is
   literally true.
2. **No process holds either environment.** `_Semantic_DB._env` is cached on the
   class for the process lifetime (`semantics.py:186`, `:285-303`) and vector
   environments in a path-keyed global (`semantic_embedding.py:1048-1065`), and
   POSIX rename does not disturb an open fd or mmap — so a live holder would keep
   writing into the rollback target. Stop the RPC host and the REPL, verify with
   `fuser`/`lsof`, and only then swap.
3. **A restarted REPL, without the interpretation driver.** Part A edits `.ML`, and
   a running server does not reload it. The previous run used a REPL restarted
   **without `INTERPRETATION_DRIVER`** (no LLM is involved in the dump); record the
   exact `repl_server.sh` invocation in the run log. Liveness is checked with `ss`
   only — **never** by connecting to :6666, which kills the server. Killing and
   restarting needs the user's say-so each time.
4. **Do not run the join concurrently with a sweep.** Not for lack of RAM —
   measured 14.2 GiB available and 39.8 GiB free swap — but because `poly` holds
   21.1 GiB swapped out, and a sweep faults that back alongside the build wrapper's
   28 GiB on a 62 GiB box.
5. **Disk.** The run holds simultaneously: the old store (1.8 G), a fresh backup of
   it and of the vector store (1.8 G + 15.6 G), the dump (~1 G), the new store
   (~2 G) and the new vector store (~15.6 G) — about **36 GiB** against 93 GiB free
   on a btrfs `/home` already at ~91 % data usage. Feasible once. Two things must be
   decided before starting: what happens to the four stale `bak-2026081*` directories
   (6.8 G), and who deletes a failed attempt. **Note also that raising
   `VECTOR_MAP_SIZE` to `1 << 36` removed a backstop**: two vector environments at a
   64 GiB ceiling each now exceed free space, so a runaway write ends in filesystem
   ENOSPC rather than a clean `MapFullError`. A disk check belongs in the run script.
6. **`isabelle build` is not run at all**, and `-c` is never passed anywhere. The
   `AFP-ALL-4` image cost 60 hours.

### B.3 Step 1 — the entity dump

A new Isa-REPL app, `Semantic_Store.dump_entities`, sweeping the cone (§B.4). For
each theory it calls `enumerate_entries` (`semantic_store.ML:1284`) — the same
enumeration a live collection performs, now with repaired keys — and sends one batch
per theory to a new Python RPC handler, which appends to a scratch LMDB
`semantics.rekey-dump.lmdb`:

- key: the **new** universal key;
- value: msgpack `(name, kind int, entity position, constituents, stating theory
  long name)`, read out of the entry tuple `(entity, name, prop, entity_pos, uk,
  hint, prov, constituents, digest, deps)` that `enumerate_entries` already returns,
  plus the theory being swept;
- plus, per theory, a **completion record** (long name → enumerated count).

`map_size` is `SEMANTICS_MAP_SIZE` (4 GiB): the live store carries every LLM
interpretation in 44 % of that, and the dump carries none.

The completion records exist because otherwise a short dump is undetectable — §B.6's
reconciliation balances identically for a dump covering 9,955 theories and one
covering 500, since leftovers are *defined* as whatever the dump did not map. The
join refuses unless the dump's theory set equals the target list.

**Parameterising `backfill_theory`, carefully.** The skeleton
(`semantic_store.ML:1863`) carries the WIP skip, two refusals, the per-theory log
line and the `schedule_dag` drive, and both passes should share it — but three of its
decisions must become parameters, not inherited:

- the **hit-shortfall gate** (`:1907-1913`, raised at `:1933-1937`) is *meaningless*
  for the dump, which never consults the store. It stays in the position-backfill
  body. The dump's own invariant is `written == enumerated`.
- the **`tie_break_degraded` and `line_mismatch` refusals** (`:1886-1893`) return
  without sending any entries. Inherited, they would turn every record of a refused
  theory into a silent leftover. **The dump must emit its entries anyway** — the
  position is advisory, the key is not — and record the refusal alongside.
- note in passing that any per-theory exception is re-raised by
  `Par_Exn.release_first` (`:1805`) and kills the whole `schedule_dag` run, not one
  theory.

Also note: `backfill_positions` itself becomes unusable between Part A landing and
Part B completing, because every recomputed key will miss.

The dump is **not** idempotent in the sense earlier claimed. Its key is the new
universal key while `enumerate_entries`' dedup is per-theory and `schedule_dag` runs
theories as parallel futures, so two theories producing one key write it twice with
scheduling-dependent `name`/`position`. The handler must detect a duplicate key,
keep both, and count them; such keys are ambiguous for the join.

### B.4 The cone the dump must cover

**The target list is `afp_all4_roots.heap.txt` (10,614 names)** — what the image
actually holds, as opposed to what any list says it should. Two reasons it is the
right source and not merely an available one: every name in it resolves by
construction, so the failure mode that killed the previous run (one unresolvable
name aborts the whole `load_theory`) cannot occur; and it is maximal, so no theory
in the image is left out by an accident of list-keeping.

Two weaker sources were considered and rejected. `afp_all4_theories.txt` is a
hand-generated *wanted* list whose session qualifiers were taken from AFP entry
**directory** names, which is wrong wherever a directory declares several sessions
(`thys/Zippy/ROOT` declares both `Zippy` and `Zip_Benchmarks`); 468 of its 9,621
names named nothing in the image. Deriving the list from the `AFP-ALL-4` ROOT chain
would be principled but still records what was *declared*, not what was *built*.

The previous sweep used the 9,153-name intersection of the wanted list and the
heap, in two passes (9,153 roots, then 660 more heap theories, 2,137 with cones).
Adopting the heap list subsumes both and adds the 1,461 image theories the
intersection had discarded — worth 6,003 records (§B.0).

Per D7 the cone stops there: records whose stating theory is not in the image are
not pursued.

Housekeeping, not on the critical path: `afp_all4_theories.txt` was repaired
anyway, since it remains the build input. 178 names were rewritten to the session
the entry's own ROOT declares and 290 dropped, leaving 9,331 that all resolve; a
first attempt that also guessed by base-name uniqueness made three errors and was
discarded rather than patched, because that rule is the very fallacy this plan
exists to fix. The pristine original is at
`afp_all4_theories.txt.bak-20260812-191926`. `migrate_entity_positions.py:139-141`
still advertises that file in its `--theory-file` help and should point at the heap
list instead.

### B.5 Step 2 — the offline join

A new script, `contrib/Semantic_Embedding/migrate_universal_keys.py`, run after the
sweep in its own process. It reads the old store and the dump and writes
`semantics.lmdb.building`.

**Which store it reads.** The **user** environment, opened directly with
`lmdb.open` — not through `Semantic_DB`'s facade, whose `_get_raw` and `iter_items`
are layered (`semantics.py:479-486`, `:548-576`): reading through them would copy
system-resident records into the new user layer, permanently shadowing later system
upgrades and defeating `purge_vectors_without_a_user_record`. Importing `semantics`
does not open the environment, so the direct open is safe. The script **asserts
`validated_system_db() is None`** and stops if a system layer is configured.

**Per dump entry:**

1. **Name-addressed keys are unchanged.** Assert it — every such key must already
   exist in the old store or be a genuinely new entity — and copy the record
   verbatim. A violation means Part A broke something it should not have touched;
   stop.
2. **Theorem-alike:** look the new key up in the old store first. A hit means the key
   did not change (common: a record collected while its own theory happened to be the
   pinned one is already correct); copy verbatim. On a miss, take the old records
   sharing the new key's **tail**, excluding tombstones, and fill **only if exactly
   one candidate survives**, or if the position discriminator below identifies one.
3. **Otherwise, do not guess.** The new key is written with no record and the entity
   goes on **the gap list** with its stating theory, name and kind.
4. **In every filled case** the record takes the dump's `name`, the dump's **entity
   position** and the dump's **corrected constituents**; `expr`, `interpretation` and
   the remaining fields come from the one chosen old record.

**The position discriminator** turns some ambiguity into certainty and is therefore
worth money, but carries no correctness: 1,092,855 old records already carry
`$AFP/<Session>/<Theory>.thy`, which names the theory the sweep found them in, and
the dump knows which theory it was enumerating. Where they agree, that candidate is
the one. Where they do not, the entity goes on the gap list. The **constituent-overlap
score is not used** — it reads the poisoned field, and precisely on the records the
migration exists to repair.

**Tombstones** (`TOMBSTONE = b""`, `semantics.py:79`, written by `delete` at
`:623-647`) are classified before decoding — `_decode` raises on `b""` (`:346`) — are
never tail-join candidates, are carried under their old keys, and are counted as
their own category. They matter even without siblings: a tombstone can sit at an old
key sharing a new key's tail, and resurrecting a deliberately deleted fact from a
sibling's content would be silent.

**Leftovers** — old records no dump entry maps: theories no sweep can load, facts
gone from source, WIP records, experience records, and the superseded halves of
drift pairs. Copied over unchanged under their old keys and counted by category.

**Theory-status records and the counter** (keys ≤ 16 bytes) are copied — their keys
are real theory hashes, unaffected — **except** that `finished` is cleared (the cost
and token fields kept) for every persistent theory that has entries on the gap list
or was not covered by the dump. This is not merely a repair of a stale flag: it is
what makes the gap list runnable, since `plan_interpretation` filters the whole cone
on `is_thy_interpreted` (`semantics.py:740`, `semantic_store.ML:1726`) and a plain
re-run would otherwise report nothing to do.

**Vectors.** One decision per new key: the record and the vector come from the **same**
chosen old key, driven by an explicit `(new key → the one old key used)` map — never
independently, because the vector-layer self-sufficiency invariant deliberately
removed the read-side backstop (`semantic_embedding.py:1306`). A new key with no
chosen source gets **no vector**; `_auto_embed` fills it after re-interpretation. The
**16-byte theory embed-status records inside each vector store are copied verbatim**
— losing them makes `is_thy_embedded` false across the board and discards the
`total_tokens` ledger (`semantics.py:1199-1201`).

### B.6 Verification gates, before any swap

Reported either way; the join refuses to promote a store that fails one.

- **Dump completeness**: the dump's theory set equals the target list.
- **Partition**: every old entity record is in exactly one category — selected as a
  fill source (with a count of how many new keys it fed), carried as a leftover, or
  carried as a tombstone — and every new key has either exactly one source or a gap
  list entry. Reported as counts per category, not as a single balancing equation.
- **No lost interpretation**: no old record's interpretation disappears without
  either being carried under its old key or feeding at least one new key.
- **Prefix check**: for every theorem-alike record in the new store, re-XOR the stored
  constituent hashes **and then OR byte 0's LSB with the constituents' WIP bits**, and
  compare to the prefix. (The plain XOR is not the prefix — `Universal_Key.ML:507`
  — and the new store carries ~21,000 WIP records.)
- **Skipped names** (§A.4) total zero across the dump.
- **Position coverage** per kind. The expectation is that the **229,267**
  memo-attributed records get positions; a residue of roughly **5,100** is expected
  and correct (the never-swept and drift populations of §B.0), so only a residue
  materially above that is a stop condition. The earlier gate, which expected all
  234,398, would have fired on a correct run.
- **Vectors**: every old vector key has at least one image, and no new key that had a
  vector loses it. Not a count-preservation check — fan-out raises the count and drift
  collapse lowers it, and the 1,363,067 baseline already exceeds the record count by
  724 because of tombstones.

### B.7 Promotion, the gap list, and getting back

`semantics.lmdb.building` is renamed to `semantics.lmdb.new` **only after every gate
passes**, and the swap refuses a bare `.building` — the same shape as
`install_system_db`'s temp-dir-then-rename with crash heal
(`snapshot_sync.py:584-650`). Then, with the preconditions of §B.2 item 2 verified,
the old directories move to `.bak-<timestamp>` and the new ones take their place.
Rollback is the same moves reversed, using the §B.2 backup rather than a renamed live
directory. The dump is kept until the new store has been exercised.

**The gap list is then filled by ordinary interpretation.** Group it by stating
theory and run collection over those theories; `interpret_file` splits entries into
cached and uncached and asks the LLM only about the uncached
(`semantic_interpretation.py:1108-1119`), and its **dry run** reports "N of M entries
need interpretation" without spending anything (`:1090-1093`). So the sequence is:
**dump → join → dry run over the gap list → the user approves the spend → the real
run → chained embed**. There is an explicit decision point before any money is spent,
and the re-generated interpretation is made in the entity's own theory context, which
is if anything more trustworthy than an inherited one.

### B.8 What this does not recover

- **19,539 records across 719 theories that are not in the `AFP-ALL-4` image** —
  `Geo_Real2` 3,349 and the Why3 verification-condition family. Abandoned by D7.
- Records for facts that no longer exist in the current sources (AFP drift: 635
  identified, plus an unknown number whose statement changed).
- WIP records (~21,000) — a disposable cache that `clean_wip` removes.
- The 20 records §B.0 cannot explain.

### B.9 What downstream users lose, for the release note

Recorded because D3 writes it off, not because the plan addresses it. After the
release, a user's own locally collected records stay under old keys and become
unaddressable; the shipped AFP corpus is unaffected, because the system DB is
re-keyed with it. Retrieval does **not** fail loudly — `topk` drops keys with no
vector and the non-reranker path materialises placeholder records carrying a name and
no interpretation (`semantics.py:2053-2062`), so the result looks like an answer. The
remedy is to re-run collection over one's own theories with **`--reinterpret`**
(`isabelle_semantics.py:1512`); a plain `collect` reports nothing to do, because the
theory-status records are keyed by theory hash and still say `finished`. AoA
experience memories cannot be regenerated this way at all — they are agent-written,
not derived from sources.

### B.10 The experience migration (D8)

**6,862 records**, 6,769 of them persistent. A separate pass, because experiences
are not enumerated from any theory: the dump never sees them, so the cone in §B.4
is irrelevant to them.

Their keys are built by `Universal_Key.compute_constituents` over the goal patterns
(`Isabelle_RPC/Tools/context.ML:1089-1091`), so the fix moves them. Worse than for
theorem records, the stored constituent list is **also the availability predicate**
at retrieval time — `all(h in loaded for _, h in rec.theory_constituents)`
(`semantics.py:1917-1922`) — so a wrongly-resolved entry silently withholds the
experience from every proof that does not happen to load the misnamed theory. That
damage exists today, independent of the fix.

The pass: for each experience record, re-parse its stored `goal_patterns` and
recompute its constituents through post-fix ML, rebuild the key, move the record,
then `Experience_Index.rebuild`. **The existing `repair_xor_prefixes` cannot be
reused** — `check_consistency` (`semantics.py:893-930`) only flags a key that
disagrees with its own stored list, and a poisoned list is perfectly self-consistent
with the key it produced, so the scan returns nothing to repair.

Scale of the damage measured before the population grew: 8 of the then-180 records
named a theory the sweep does not resolve to, 2 of them persistent, all on the base
name `Approximation`. That is a lower bound — a record that stored the *winner*
while its patterns needed the loser looks clean to that test.

**Concurrency.** 6,682 of these were written on the afternoon of 2026-08-12, i.e.
the store is a live target. The join reads the old store and the swap replaces it;
anything written in between is lost at swap time. Either the writer is stopped for
the window, or the join is followed by a delta pass. The user reports the writing
run has finished, so a stop is the simpler option — but it has to be confirmed at
the moment of the run, not assumed from this sentence.

# Part E — review record

Two adversarial rounds: five reviewers by lens (Part A correctness, Part B data
integrity, `cslh19` operability, factual audit, consumers outside the store), then
three refuters. 54 findings; 4 refuted outright, 14 narrowed, 36 confirmed and folded
into the text above. The four refuted are recorded so they are not raised again:

- **`Cannot_Hash` newly exposed by the fix.** False premise: `enumerate_entries`
  (`semantic_store.ML:1589`) and `backfill_theory` (`:1867`) already call `hash_of` on
  every theory in the cone, and `hash_of` recurses over all parents, so every "losing
  sibling" is already hashed today. The fix adds no theory to the hashed set.
- **`Thy_Info` staleness flipping the WIP bit and misleading `clean_wip`.** The
  WIP/persistent branch is chosen by `Resources.loaded_theory` on the long **name**
  (`theory_hash.ML:147`), so two theory values sharing a name always land in the same
  branch and always agree on the LSB.
- **No stop-then-start sequence for the REPL.** §B.2 already requires a restarted
  server, user approval per restart, and `ss`-only liveness; nothing proposes a second
  port.
- **The two performance measurements were one measurement reported twice.** They used
  different populations and different metrics. The real error was claiming that "two
  independent measurements agreed" on a figure only one of them produced.

One structural conclusion from round 1 was **withdrawn by the user, correctly**: the
review treated "Part A ships without Part B" as the headline risk and built a
key-scheme marker, a `SCHEMA_VERSION` bump, a CI gate and a publication freeze on top
of it. That scenario does not arise (D3), and the whole edifice is gone.
